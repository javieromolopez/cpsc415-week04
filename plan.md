# Plan: Ask the course

## What this plan executes
The steps below build `spec.md`'s two components — **Indexer** (`rag_index.py`, embeds the corpus to `index.json`) and **Asker** (`rag_ask.py`, CLI front-end with `--no-retrieval`) — plus the eval runner that verifies them. Each step names the numbered `spec.md` behaviors it satisfies.

## Files to create or change
| File | Purpose |
|---|---|
| `pyproject.toml` | uv project config: Python 3.10+, dependencies (`httpx`, `numpy`). Per `CLAUDE.md`: standard library + minimal libs. |
| `rag_index.py` | **Indexer** component. Walks `syllabus.md`, `assignments/`, `weeks/01`–`weeks/03`; ATX section parser; sentence-aware chunker; OpenRouter embedder; **`index.json` cache** (not `.pkl`) with mtime invalidation. |
| `rag_ask.py` | **Asker** component. `argparse` CLI for `question` + `--no-retrieval`; two-stage refusal (cosine threshold → prompt grounding); format answer + citations + retrieved chunks with raw cosine scores. |
| `questions.json` | Authored by the student (not the agent). Five eval questions: 3 single-place, 1 multi-source synthesis, 1 out-of-scope. Each entry: `question`, `expect` (`answer`/`refuse`), `why`. |
| `eval_runner.py` | Loops `questions.json` × 2 modes, scores pass/fail, writes `CHECKS.md`. |
| `CHECKS.md` | Generated by `eval_runner.py`. Per-question rows + two totals. |

## Order of work

### 1. Project bootstrap
- Create `pyproject.toml` with `httpx` and `numpy`; run `uv sync`.
- Read `OPENROUTER_API_KEY` from env; fail loudly if missing.
- **Behaviors:** prerequisite for all behaviors.

### 2. Corpus loader + Markdown section parser (in `rag_index.py`)
- Walk only the allowed paths; skip `weeks/04`, `slides/`, `README.md`, anything not `.md`.
- Parse ATX headings (`#`, `##`, `###`); emit `(source_path, section_heading, text)` per section. Headings inside fenced code blocks are ignored.
- **Behaviors:** #1 (corpus scoped correctly), #2 (chunks carry source metadata).

### 3. Chunker
- Split each section into chunks of **~800 chars with ~100-char overlap, on sentence boundaries** (`. `, `.\n`, `? `, `! `). Each chunk keeps its `section_heading` metadata.
- **Empirical tuning:** before sentence-aware chunking, **prepend the section heading to the chunked text** so the embedder captures the heading topic in addition to the body. The `section_heading` field on each chunk is unchanged — citations still use the parsed heading — but the embedded text starts with the heading line. This fixes the case where the answer lives in a short heading but the body is on an unrelated topic (e.g., `### Week 6 — Monday, October 26 (mid-term)` whose body is about image generation). Without prepending, that section ranked 15+ (score 0.17); with prepending, it ranks 8 (score 0.33) for "When is the midterm?".
- **Behaviors:** #2 (chunks carry source metadata), #3 (sentence-aware chunks).
- **Why ~800 chars / ~100 overlap?**
  - **Markdown section headers are short (~30–80 chars, e.g., `## 4. The second model`).** An 800-char chunk holds the heading + most of its body in one piece, so retrieval sees one self-contained "fact" rather than splitting a section across many chunks.
  - **Policy passages in the corpus** (`syllabus.md`'s *Late Submission Policy*, *Course Description*, etc.) run 600–1,200 chars; section bodies in `weeks/0X/lab.md` are 200–600 chars per paragraph. 800 chars fits one long paragraph or two short ones — enough to be a self-contained rule, not so large that retrieval scores dilute.
  - **The 100-char overlap** is large enough to keep a trailing half-sentence visible in the next chunk, so a query near a boundary still hits the chunk containing the next paragraph.
  - **Sentence-aware splitting** prevents orphan sentences like `"Late days may be applied to any assignment and used indi-"` / `"vidually or together."` — the chunker extends each cut to the next sentence boundary before advancing, so no chunk ends mid-sentence and the overlap is genuinely redundant, not garbage.

### 4. Embedder + index (Indexer component) + baseline disagreement observation
- Embed each chunk via OpenRouter `/embeddings` with `openai/text-embedding-3-small` (one batched call).
- Store vectors + metadata as JSON in **`index.json`** (vectors as nested lists — `numpy.save` writes binary `.npy` and is not JSON-portable, per the lab requirement); record corpus max mtime alongside for cache invalidation.
- Retriever: embed the query with the same model; compute raw cosine similarity; return top-k with scores.
- **Behaviors:** #4 (index cached to JSON, mtime-invalidated), #7 (threshold gate feeds off retriever scores), #11 (raw cosine scores printed).
- **Baseline disagreement observation (no fix in v1):** When two chunks disagree on a fact — e.g., `weeks/01/lab.md` states one model name and `weeks/03/lab.md` states a different one — the retriever **surfaces both chunks** because both score highly on cosine similarity. The retriever does **not** weight by recency or file path. The LLM then synthesizes from the retrieved excerpts and may report the **stale answer** from the older chunk. We **record this as an observation** in `CHECKS.md` (not a failure), so the grader can see exactly what the baseline does. Recency weighting or a disagreement protocol is **out of scope for this lab** — it would be a future intent.

### 5. CLI (Asker component, `rag_ask.py`)
- `argparse`: `question` (positional) + `--no-retrieval` (flag).
- Two-stage refusal: cosine threshold → prompt grounding with strict "answer only from excerpts" system instruction.
- Format stdout: answer → `Citations:` block (`- file > section`) → `Retrieved chunks:` block with raw cosine scores.
- On refusal: print exactly `I can't find that in the course documents.` and exit 0.
- **Empirical tunings:**
  - **`TOP_K = 10`** (raised from the originally proposed 5) so the mid-ranked chunk that carries the answer — e.g., `Week 6 — Monday, October 26 (mid-term)` at rank 8 with score 0.33 — actually reaches the LLM's prompt. With `TOP_K = 5` that chunk is outside the top-k and the LLM refuses.
  - **Cosine threshold = `0.30`** (lowered from the originally proposed `0.5`) after measuring this corpus's score distribution. Observed top scores for in-scope queries cluster at 0.37–0.40; the proposed `0.5` would refuse every query. The threshold still rejects clearly unrelated text (the sanity check on "How do I cook pasta?" scored 0.05).
- **Behaviors:** #5 (CLI accepts a single question), #6 (`--no-retrieval`), #7 (programmatic refusal), #8 (prompt-grounding refusal), #9 (exact refusal string), #10 (citations), #11 (chunks + raw scores), #12 (disagreement protocol).

### 6. `questions.json` (authored by the student)
- 3 single-place facts (e.g., midterm date, grading weight, a lab step), 1 multi-source synthesis (e.g., late-day policy touching both syllabus and an assignment), 1 out-of-scope.
- Each entry: `question`, `expect` (`answer` or `refuse`), `why`.
- **Behaviors:** #13 (eval runner uses these).

### 7. Eval runner (`eval_runner.py`)
- Loop over `questions.json` × 2 modes, capture stdout, score against `expect`, write `CHECKS.md` with per-question rows and totals.
- **Behaviors:** #13.

### 8. Run + verify
- Execute the eval runner.
- Open `CHECKS.md`. Confirm **5/5 with retrieval**, **1/5 without** (only the out-of-scope question).
- **Behaviors:** all of them, end-to-end.

## Risks
- **Embedding model quality.** `text-embedding-3-small` is the cheap default; if it ranks course jargon poorly, swap for `text-embedding-3-large`. **Notice:** top-k for known-relevant queries is below threshold → swap.
- **LLM refusal faithfulness.** `minimax/minimax-m3` may paraphrase "I can't find that..." in the prompt-grounding stage. **Notice:** in-scope question refuses with non-canonical string → tighten the prompt or swap to a frontier model.
- **Stale-answer surfacing (baseline).** When two pages disagree and both score highly, the model can report the older one. **Notice:** `CHECKS.md` shows an answer for a fact that has since changed in a later week; this is the observation the spec promises to record.
- **Without-retrieval determinism.** Without chunks, the model might recall an answer from training, raising the without-retrieval pass count. **Notice:** the without-retrieval total exceeds 1/5 → the model is leaking training knowledge; tighten the eval set or pick a less-trained model.
- **Cache staleness.** A corpus edit + no rebuild → stale chunks. **Notice:** edit a known file, re-run, confirm chunks change.
- **API rate limits.** 429s during the eval run (10 calls in close succession). **Notice:** retry log shows 429s; intermittent eval failures.
- **Env var.** Missing `OPENROUTER_API_KEY`. **Notice:** startup crash with a clear message naming the env var.
- **Refusal string variations.** Whitespace, trailing newline, or punctuation differences. **Notice:** eval runner matches with `==` after normalization; mismatches show the actual string in `CHECKS.md`.

## Subagents and parallel work
- **Question authoring** (step 6) is owned by the student; per the lab instructions, the user authors `questions.json` themselves. No subagent delegation for this step.
- **Chunker unit tests** could be delegated to a tester subagent, but it's small enough to do inline.
- Everything else is sequential: index → retriever → CLI → eval runner. No parallel work to claim.

## Proof
- `uv sync` exits 0.
- `python -c "from rag_index import retrieve; print(retrieve('When is the midterm?', k=5))"` returns a non-empty list with cosine scores.
- `python rag_ask.py "When is the midterm?"` prints answer + citations + chunks with scores; exits 0.
- `python rag_ask.py "Who is the instructor's PhD advisor?"` prints exactly the refusal string; exits 0.
- `python rag_ask.py "When is the midterm?" --no-retrieval` runs without a `Retrieved chunks:` block.
- `python eval_runner.py` exits 0 and writes `CHECKS.md`.
- `CHECKS.md` shows **5/5 with retrieval** and **1/5 without** (only the out-of-scope question). Any other result triggers tuning.
